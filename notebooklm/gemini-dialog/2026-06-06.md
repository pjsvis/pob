Your Mac M-chip is hiding a secret: it can fine-tune a real language model from scratch in under 3 minutes or depending on the dataset longer, maybe 10 minutes . No need to rent a cloud GPU rental, thus no cloud bill, and with uv you have nearly no Python environment hassle.
Here’s how I turned a tiny 270M model into a blazing-fast, opinionated code reviewer that runs entirely offline. The before/after is very clear. Let me show you.
Of course, this “code reviewer” is everything else than to be taken seriously, since the data set we use here is a toy dataset.
All we want here is just to demonstrate on a toy dataset and a nearly toy model — that is we use the older Gemma 3 model to reduce time and energy wasted on this experiment and not the more capable Gemma 4 small models — that you can fine-tune small, tiny LLMs on your laptop with drastic behavioral change of the model — just from few hundred samples.
Just that you can say: I fine-tuned an LLM once. And it worked! And the entire thing takes few minutes!
The model: Gemma 3 270M Google just released it in Aug 2025.
It’s 270 million parameters — tiny enough to fine-tune on an M1 Air, fast enough to generate 150+ tokens/second on an M3.
What makes it special: it was purpose-built for task-specific fine-tuning, with strong instruction-following baked in before you even touch it.
270M params ~830MB RAM 150+ tok/s on M3 (model size is currently 827 MB)
The use case I picked: automated code review. You paste Python code, it replies like a senior engineer — pointing out bugs, style issues, and security holes. Base model? Useless for this. Fine-tuned model? Quite good. Let’s build it.

Step 3 — Fine-tune with LoRA (the magic happens here)
LoRA (Low-Rank Adaptation) freezes 99% of the model weights and only trains a tiny set of adapter matrices. For 270M, this means the fine-tune uses ~80MB of GPU RAM and completes in minutes.
In the terminal, fine-tuning is just one command:
uv run mlx_lm.lora \
  --model mlx-community/gemma-3-270m-it-bf16 \
  --data ./data \
  --train \
  --iters 300 \
  --batch-size 2 \
  --num-layers 8 \
  --learning-rate 2e-4 \
  --adapter-path ./adapters/code-reviewer \
  --save-every 100 \
  --val-batches 4
What each flag does:
--iters 300       Training steps. 200-400 is ideal for 50 examples.
--batch-size 4  Safe for all M-chips including M1 Air (8GB).
--num-layers 8    How many transformer layers get adapters.
                  More layers = smarter but slower. 8 is a sweet spot.
--learning-rate   2e-4 is the MLX community standard for Gemma.
--adapter-path    Where to save the trained LoRA weights (~10MB total).

The first model did not fail because LoRA is bad. It failed because I asked a tiny model to learn “senior Python code review” from a too tiny set of examples which hardly showed a lot of variation.
One important nuance: validation loss does not always need to sit close to train loss in a tiny chat fine-tune, especially when the validation examples differ in length and pattern. But when train loss collapses toward zero while validation barely improves, yes, the model is mostly memorizing your examples.
For this demo, I would judge success by three things:
1. Does valid loss improve before train loss collapses?
2. Does the model still review unseen snippets correctly?
3. Does novel_test reveal some transfer, not just template replay?
The best checkpoint is probably not the final one.
I would test checkpoints at 150, 200, 250, and 300 iterations, too. For a 270M model, “slightly undertrained but general” is much better than “perfectly memorized and confidently useless.”

Step 5 — Build a real CLI tool around it
Fine, you’ve got a model. Now make it actually useful: a review command that reads any Python file and prints feedback.
nano review.py
#!/usr/bin/env python3
"""
Usage: uv run review.py mycode.py
       uv run review.py mycode.py --temperature 0.2
       cat mycode.py | uv run review.py -
       ai-review mycode.py          (after uv tool install .)
       ai-review mycode.py --temperature 0.5
"""
import sys
import argparse
from mlx_lm import load, generate
from mlx_lm.sample_utils import make_sampler

MODEL_ID    = "mlx-community/gemma-3-270m-it-bf16"
ADAPTER     = "./adapters/code-reviewer"
MAX_TOKENS  = 350
CHUNK_LINES = 40

def make_prompt(tokenizer, code: str) -> str:
    messages = [
        {"role": "user", "content": f"Review this Python code:\n\n```python\n{code}\n```"}
    ]
    return tokenizer.apply_chat_template(
        messages,
        tokenize=False,
        add_generation_prompt=True,
    )

def chunk(lines: list, size: int):
    for i in range(0, len(lines), size):
        yield "\n".join(lines[i:i + size]), i + 1, min(i + size, len(lines))

def main():
    parser = argparse.ArgumentParser(description="AI code reviewer powered by Gemma 3 270M")
    parser.add_argument("file", help="Python file to review, or '-' for stdin")
    parser.add_argument(
        "--temperature", "-t",
        type=float,
        default=0.1,
        help="Sampling temperature (default: 0.1). Lower = more deterministic, higher = more creative.",
    )
    args = parser.parse_args()
    src = sys.stdin.read() if args.file == "-" else open(args.file).read()
    lines = src.splitlines()
    sampler = make_sampler(temp=args.temperature)
    print(f"Loading fine-tuned code reviewer... (temperature={args.temperature})")
    model, tok = load(MODEL_ID, adapter_path=ADAPTER)
    print(f"Model ready - reviewing {len(lines)} lines\n")
    for code_chunk, start, end in chunk(lines, CHUNK_LINES):
        print(f"{'─' * 50}")
        print(f"Lines {start}–{end}:")
        print(f"{'─' * 50}")
        prompt = make_prompt(tok, code_chunk)
        result = generate(model, tok, prompt, max_tokens=MAX_TOKENS, verbose=False, sampler=sampler)
        print(result.strip())
        print()

if __name__ == "__main__":
    main()

That is a compelling technical direction. Given the "darts in the dark" experience with vector steering, shifting to model fine-tuning—specifically for structured output consistency—is a logical evolution. You are essentially treating the model's behavior as a deterministic component of the system rather than a probabilistic variable.


Using your `typescript-hono-playbook.md` as the core of a training set is highly viable. You have already defined strict architectural invariants in that document, which makes it an excellent "schema" for fine-tuning a small model (like the Gemma 3 270M mentioned) to act as a **code generation or compliance agent** that adheres to your specific constraints.


Here is an analysis of how to bridge your playbook into that training pipeline:


### The "Playbook-to-Model" Pipeline
To make this work, you need to transform the "Rules" and "Wrong patterns" from your markdown file into a JSONL format that the model can ingest.


1. **Generate Synthetic Training Data:**

- Since you have a list of "Banned" patterns (e.g., string concatenation for HTML, inline `<script>` tags), you can write a script to generate hundreds of examples of "Bad Code" paired with the "Correct Refactor" based on your playbook.
- **Example entry:**

```
{
  "messages": [
    {"role": "user", "content": "Refactor this TypeScript Hono route to follow the Playbook rules:\n\n```typescript\nel.innerHTML = '<table>' + rows.map(...).join('') + '</table>';\n```"},
    {"role": "assistant", "content": "Correct pattern: Use a JSX component.\n\n```tsx\nreturn c.html(<PositionsTable positions={enriched} />);\n```"}
  ]
}

```

2. **Constraint Enforcement via Fine-tuning:**

- By training on these examples, you are not just teaching it code; you are teaching it the **"minimalist aesthetic"** you prefer.
- The model learns the *association* between "Server-rendered HTML requirement" and "JSX component output," which reduces the reliance on prompting it to "be more like your playbook."

### Strategic Considerations for your Stack

- **Small Models as "Linters":** Instead of just using the model for code generation, you could fine-tune a tiny model specifically to act as a *pre-commit validation agent* that scans files and flags violations of your `Architecture Invariants` table.
- **The "Justify Engine" integration:** You mentioned the Justify Engine as a core process. You could fine-tune the model to output a `justification` field for every code change, ensuring the model's reasoning aligns with your Scottish Enlightenment-inspired grounding framework before the code is even applied.
