This is a distinction between a specialized **native binding** and a universal **WASM abstraction**.


Here is the analytical map of the territory comparing **`sql.js`** and **`bun:sqlite`**.


### Core Distinction: Substrate vs. Simulation

- **`bun:sqlite` (Native):** This is a high-performance, native binding built directly into the Bun runtime. It interacts with the SQLite C API using Bun’s foreign function interface (Zig/C++). It operates directly on the "metal" of the file system.
- **`sql.js` (WASM):** This is SQLite compiled to WebAssembly. It runs in a virtualized sandbox (the WASM memory heap). It simulates a file system within that heap, requiring manual bridging to persist data to the actual disk.

### Comparative Matrix


| Feature | **bun:sqlite** | **sql.js** |
| --- | --- | --- |
| **Primary Context** | **Bun Runtime Only** (Server-side) | **Universal** (Browser, Node, Bun, Deno) |
| **Performance** | **Extremely Fast.** Approx 3-6x faster than `better-sqlite3`. | **Slower.** Incurs WASM bridging overhead; typically 50-60% performance of native. |
| **Persistence** | **Direct.** Reads/writes to disk (`.sqlite` files) natively (WAL mode supported). | **Manual.** Loads entire DB into memory. You must export the byte array to save it. |
| **Memory** | **Efficient.** Pages data from disk as needed. | **High Load.** Must load the *entire* database file into the WASM heap. |
| **API Style** | Synchronous (mostly), simple, native feel. | Synchronous (in-memory), explicit initialization. |
| **Dependencies** | **Zero.** Built-in to Bun. | **External.** Requires the `sql.js` library and WASM binary. |


---

### Detailed Mentation
#### 1. `bun:sqlite` (The Native Powerhouse)
If you are strictly within the Bun ecosystem ("Sleeve"), this is the optimal choice. It is engineered for speed, utilizing highly optimized C/Zig bindings that bypass the V8/JavaScriptCore overhead found in other adapters.


- **Key Advantage:** It supports "zero-copy" operations where possible and handles transactions and prepared statements with native efficiency.
- **Constraint:** It is a "Walled Garden" tool; code written for `bun:sqlite` will not run in Node.js or the browser without a polyfill or abstraction layer (like Drizzle ORM).

#### 2. `sql.js` (The Universal Adapter)
This is a port of portability. Because it runs in WASM, it creates a consistent SQLite environment anywhere JavaScript runs.


- **Key Advantage:** It allows you to run a full SQL database *inside a user's web browser* without a backend, or in environments where installing native C-bindings is impossible.
- **Constraint:** The "Persistence Paradox." Since it lives in memory, if the script ends or the tab closes, the data is lost unless you manually export the binary data and save it to a file or local storage.

### Operational Heuristic: Selection Strategy

- **Use `bun:sqlite` if:** You are building a backend service using Bun. The performance gains and file-system integration are superior. It is the "correct" usage of the substrate.
- **Use `sql.js` if:** You need to run SQLite in the **browser** (client-side), or if you need a purely in-memory database for testing that behaves exactly the same across Node, Bun, and Chrome.
