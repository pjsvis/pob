### Internal Brief: SQLite Configuration Audit & Stabilization
**Priority:** High

**Focus:** Database Integrity, Multi-process Synchronization, and Resource Management


#### Overview
Current observations indicate occasional database corruption and "stale state" issues during concurrent access by the CLI, API server, and TUI monitor. An audit of the persistence layer reveals inconsistent SQLite configurations and high-risk checkpointing logic that likely contribute to these failures.


#### 1. Lack of Uniform Schema Enforcement
While the schema defines complex relationships (e.g., `issue_dependencies`), the primary database connection in `internal/db/db.go` does not enable foreign key constraints.


- **The Risk:** Mutations via the CLI can result in orphaned records or broken relational integrity, which the application assumes is handled at the driver level.
- **Recommendation:** Ensure `PRAGMA foreign_keys=ON` is executed on every connection initialization across all packages.

#### 2. Race Conditions in WAL Checkpointing
All database wrappers currently execute `PRAGMA wal_checkpoint(TRUNCATE)` during the `Close()` sequence.


- **The Risk:** In a multi-process environment, a `TRUNCATE` checkpoint will fail if other processes (like a background monitor) are still attached to the shared-memory (`-shm`) file. If the CLI exits after a failed truncate, it may leave the WAL in an inconsistent state for the next process.
- **Recommendation:** Move away from aggressive `TRUNCATE` on close. Rely on SQLite’s autocheckpoint features or use `PASSIVE` checkpoints to avoid blocking concurrent readers/writers.

#### 3. TUI Connection Lifecycle & Reference Counting
The `sharedDB` pattern in `pkg/monitor/dbpool.go` manages singleton connections to prevent file descriptor leaks caused by `tea.Model` value-copying.


- **The Risk:** The current reference counting is "soft." If a model is abandoned without an explicit call to `releaseSharedDB`, or if a component bypasses the pool, the connection remains open. Over time, this leads to an accumulation of open file descriptors and potential locking contention.
- **Recommendation:** Audit the TUI `Update` and `View` cycles to ensure a deterministic "cleanup" path for shared database handles, possibly tied to a dedicated shutdown command.

#### 4. Operational Heuristic vs. SQLite Locking
The CLI uses a custom `withWriteLock` (file-based locking) to serialize writes.


- **The Risk:** This mechanism is independent of SQLite’s internal locking. If the API server (via `ProjectDBPool`) writes to the same database using standard SQLite locks while the CLI holds a file-lock, the two synchronization methods may not respect each other, leading to `busy_timeout` errors or journal collisions.
- **Recommendation:** Align the "Operational Heuristic" file-locking with SQLite’s internal locking states or consolidate write operations through a single locking authority.

#### Proposed Action Plan

1. **Centralize Connection Logic:** Create a internal utility to return a pre-configured `*sql.DB` with mandatory pragmas (`WAL`, `busy_timeout`, `foreign_keys`).
2. **Refactor Checkpointing:** Standardize on a safer checkpointing strategy that does not attempt to truncate the WAL file on every process exit.
3. **Harden the Monitor Pool:** Add logging to `getSharedDB` and `releaseSharedDB` to track connection leakage during TUI sessions.

### Gemini

I have reviewed the SQLite configuration across the `td` repository. Your suspicion regarding legacy or inconsistent configurations is well-founded; while the project correctly implements modern SQLite best practices like **WAL mode**, there are several risks related to connection pooling, checkpointing, and multi-process access that could lead to the corruption or "stale state" issues you are experiencing.


### 1. The "Abandoned Connection" Risk in TUI Updates
The most significant risk identified is in the monitor's TUI implementation. As noted in `pkg/monitor/dbpool.go`, Go's `tea.Model` often uses value receivers, which creates copies of the model during every `Update()` call.


- **The Issue:** If a model holds a database handle and is copied frequently, the original `sql.DB` instance can be "abandoned" before being closed.
- **The Consequence:** While the `sharedDB` singleton pattern in `pkg/monitor/dbpool.go` attempts to mitigate this by reference counting, any part of the UI that bypasses this pool or fails to call `releaseSharedDB` will leak file descriptors. In SQLite, leaked descriptors—especially those holding locks or shared memory (`-shm`) mappings—are a primary cause of "database is locked" errors and potential WAL corruption if a process crashes while holding those handles.

### 2. Inconsistent Pragma Application
There is a lack of "Uniform Pragma Enforcement" across the different database opening logic in the project:


- **Missing Foreign Keys:** `internal/db/db.go` (the primary issue database) **does not** enable `PRAGMA foreign_keys=ON`, whereas `internal/serverdb/serverdb.go` and `internal/api/dbpool.go` do. This can lead to orphaned records in `issue_dependencies` or `board_issues` if parent issues are deleted, potentially causing application-level "corruption" of data relationships.
- **Synchronous Mode:** All modules set `PRAGMA synchronous=NORMAL`. While this is the recommended setting for WAL mode, it is only safe if the application strictly manages its own checkpoints.

### 3. High-Risk "TRUNCATE" Checkpoints on Close
All database wrappers (`db.go`, `api/dbpool.go`, and `serverdb.go`) attempt to run `PRAGMA wal_checkpoint(TRUNCATE)` immediately before closing the connection.


- **The Risk:** A `TRUNCATE` checkpoint attempts to move all data from the WAL file back into the main `.db` file and then resets the WAL file to zero bytes. If this fails due to a "busy" database (common in multi-process environments), the WAL remains.
- **The Legacy Conflict:** If one process (like the `td` CLI) closes with a failed truncate while another process (like the `monitor` or `api`) is still attached to the `-shm` file, you can end up with a mismatch between the shared memory index and the actual WAL content.

### 4. Multi-Process Contention (CLI vs. Server)
The `internal/db/db.go` implementation uses a custom `withWriteLock` using an "Operational Heuristic" (a `.lock` file) to prevent concurrent writes from multiple processes.


- **Potential Flaw:** This file-based lock is independent of SQLite’s internal locking. If the CLI uses `withWriteLock` but the API server (using `ProjectDBPool`) writes to the same file using standard SQLite locks, they may collide. SQLite's `busy_timeout` is set to 5000ms, but if the file-lock is held indefinitely by a hung process, the SQLite connection may eventually time out or error out in a way that leaves the journal in an inconsistent state.

### Recommended Fixes
To stabilize the SQLite persistence layer, I recommend the following changes:


1. **Standardize Open Logic:** Consolidate all `sql.Open` calls into a single internal package that enforces `foreign_keys=ON`, `journal_mode=WAL`, and `busy_timeout=5000` for every connection.
2. **Audit TUI Lifecycle:** Ensure that every `tea.Model` that uses `getSharedDB` has a guaranteed path to call `releaseSharedDB`, perhaps by tying it to a `tea.Quit` command or a specialized "Shutdown" message.
3. **Refine Checkpointing:** Replace the aggressive `TRUNCATE` checkpoint on every `Close()` with a more passive `PASSIVE` or `RESTART` checkpoint, or rely on SQLite's automatic checkpointing (defaulting at 1000 pages). Explicitly truncating on every close is often unnecessary and increases the chance of "database is locked" errors during shutdown.
4. **Verify Worktree Redirection:** Ensure `ResolveBaseDir` (which handles `.td-root` files) is perfectly atomic. If two processes resolve to the same database but use different relative paths for their own file-locking, the `withWriteLock` mechanism will fail.

### Gemini

The "Silo" project can leverage several advanced CLI patterns to transform a standard `justfile` into a highly discoverable, professional-grade interface. By moving away from a flat list of commands and toward a **hierarchical, namespaced** structure, you ensure manageability as the project scales.


### 1. Architectural Patterns for `just`
To optimize discoverability, move from a "flat file" to a "modular" or "namespaced" approach.


#### A. The Namespacing Pattern (Prefixing)
Since `just` lists recipes alphabetically by default, use functional prefixes to group related commands. This creates "pseudo-folders" in the `--list` view.


- **Pattern:** `[domain]-[action]`
- **Examples:** `db-migrate`, `db-seed`, `test-unit`, `test-e2e`, `ops-deploy`.
- **Benefit:** When a user runs `just`, similar commands are visually grouped together.

#### B. The Module Pattern (Import/Export)
Use the `mod` attribute to include separate files for different domains. This keeps the root `justfile` clean and delegates specific logic to sub-files.


```
# Root justfile
mod db "tooling/just/db.just"
mod app "tooling/just/app.just"

# Display help by default
default:
    @just --list

```


- **Usage:** `just db migrate` or `just app restart`.
- **Benefit:** Developers working on the frontend don't need to parse 50 lines of database migration logic.

### 2. Enhancing Discoverability
Discoverability is the "First Mile" of developer experience (DX).


- **The "Internal" Recipe Pattern:** Prefix internal helper recipes with an underscore (e.g., `_check-deps`). These are hidden from `just --list` by default, reducing clutter for the end-user.
- **The Doc-Comment Header:** `just` pulls the comment immediately preceding a recipe as its description. Use a consistent format:

```
# [Category] Description of what this does
build-prod:
    cargo build --release

```

- **Custom Help Recipes:** Instead of relying on the default list, create a `help` recipe that uses `fzf` (Fuzzy Finder) for interactive discovery.

### 3. Utility Scripts & "The Wrapper" Pattern
`just` is a command runner, not a logic engine. For complex "Silo" operations, use **Utility Scripts** behind a `just` facade.


- **The `bin/` or `scripts/` Directory:** Store complex logic in Bash, Python, or Rust scripts.
- **The Just-Proxy Pattern:**

```
# Interactive environment setup
setup:
    @./scripts/setup_env.sh --interactive

```

- **The Justify Engine Integration:** Since the "Justify Engine" is core to your process, use `just` to enforce it. Create a `justify` recipe that acts as a gatekeeper:

```
# Submit a change with Justify Engine validation
commit msg:
    @./scripts/justify_engine.py --validate "{{msg}}"
    @git commit -m "{{msg}}"

```


### 4. Advanced "Silo" Optimization (Operational Heuristic)
Applying the **Operational Heuristic** (analyzing systems by how they are actually operated), your `justfile` should reflect the lifecycle of the project:


| Phase | Just Verb Prefix | Example Command |
| --- | --- | --- |
| **Ignition** | `init-` | `just init-dev` (sets up local env) |
| **Construction** | `build-` | `just build-wasm` |
| **Verification** | `check-` | `just check-all` (lint + test + audit) |
| **Operation** | `run-` | `just run-silo` |
| **Destruction** | `clean-` | `just clean-volumes` |

### 5. Implementation Checklist for Silo

1. [ ] **Adopt the "Double-Colon" Module Syntax:** Use `mod` for major subsystems (e.g., `just silo::start`).

3. [ ] **Use `set positional-arguments := true`:** This allows for more natural CLI-like syntax: `just db migrate 20231010` instead of `just db-migrate version=20231010`.
4. [ ] **Create a `doctor` command:** A `just doctor` recipe that runs a script to verify all local dependencies are installed. This is the ultimate "Manageability" win.
