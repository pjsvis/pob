### Gemini

The short answer is **no**. You do not *have* to bundle your MCP server as a single-file binary.


While single-file binaries (like those compiled from Go/Rust or bundled with tools like `pkg` for Node) are convenient for distribution, the Model Context Protocol (MCP) itself does not strictly require them.


Here is a breakdown of why this is the case, the different ways you can run an MCP server, and when you should choose one over the other.


---

### How MCP Clients Run Servers
Most local MCP clients (like Claude Desktop) operate by simply **spawning a subprocess**.


The configuration file asks for a `command` and `args`. As long as the command you provide creates a running process that communicates over `stdio` (standard input/output), the client does not care if that process is a compiled binary, a Python script, or a Node.js runtime executing a JavaScript file.


### Common Alternatives to Binaries
Here are the three most common ways to configure an MCP server without compiling a binary:


#### 1. Running via Language Runtime (Node/Python)
If you know the user has the necessary environment installed (e.g., Node.js or Python), you can point directly to the source script or an entry file.


**Example `claude_desktop_config.json`:**


```
{
  "mcpServers": {
    "my-script-server": {
      "command": "node",
      "args": ["/absolute/path/to/my-server/build/index.js"]
    }
  }
}

```

#### 2. Running via Package Runners (`npx` or `uvx`)
This is currently the most popular method for community servers. It allows users to run your server without manually installing it or managing versions, provided they have `npm` or `uv`.


**Example `claude_desktop_config.json`:**


```
{
  "mcpServers": {
    "sqlite-server": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-sqlite", "--db", "/path/to/db.sqlite"]
    }
  }
}

```

#### 3. Running via Docker
If your server has complex dependencies (like database drivers or system libraries) that are hard to bundle, you can run the server inside a container.


**Example `claude_desktop_config.json`:**


```
{
  "mcpServers": {
    "docker-server": {
      "command": "docker",
      "args": ["run", "-i", "--rm", "my-mcp-image"]
    }
  }
}

```

*Note: The `-i` (interactive) flag is crucial here to keep `stdio` open.*

### When Should You Bundle as a Binary?
Even though it isn't required, bundling (using Go, Rust, or Node executables) is often done for specific reasons:


- **Portability:** The end user does not need to install Node.js, Python, or PIP. They just download one file and it works.
- **Performance:** Binaries (especially Go/Rust) generally start up faster than spinning up a full Node/Python runtime.
- **Obfuscation:** If you are distributing proprietary logic and don't want to ship raw source code (though typically less of a concern for internal tools).

### Summary Table


| Method | Pros | Cons | Best For |
| --- | --- | --- | --- |
| **Source / Runtime** | Easiest to debug; Instant changes. | Requires user to have runtime (Node/Python) installed. | Development & Internal Teams |
| **`npx` / `uvx`** | Zero-setup for users; Always runs latest version. | Slightly slower startup; Requires internet for first run. | Public Open Source Tools |
| **Docker** | Total environment isolation. | Heavy; Requires Docker Desktop to be running. | Complex Dependencies |
| **Binary** | Fast; No dependencies required on host. | Harder to debug; Must compile for different OSs (Mac/Win/Linux). | Commercial Distribution |
