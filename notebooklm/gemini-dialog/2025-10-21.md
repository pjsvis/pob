### Gemini

This is a classic and frustrating issue, almost always a "where am I?" problem. The core issue is a mismatch between the **Current Working Directory (CWD)** of the running Bun process and the **relative path** (`./www/...`) you've provided.


Your `[TEST-VIZ] File exists: false` log is the "smoking gun." It proves this isn't a Hono-specific problem, but a fundamental file path resolution failure in the Bun runtime.


Here’s a breakdown of the causes and a clear plan to fix it.


---

## The Root Cause: `process.cwd()` vs. `import.meta.dir`
The primary cause is your use of a relative path (`./www/sigma-viz/dist`).


1. **Relative to CWD:** A path starting with `./` is resolved relative to the **Current Working Directory (CWD)**, which you can check with `console.log(process.cwd())`.
2. **Where is CWD?** The CWD is the directory where you *ran the `bun run` command*, not the directory where your `app.ts` file lives.

- If you are in `/project-root/` and run `bun run src/server/app.ts`, your CWD is `/project-root/`. Your relative path `./www/sigma-viz/dist` *should* work.
- If you are in `/project-root/src/server/` and run `bun run app.ts`, your CWD is `/project-root/src/server/`. The path `./www/sigma-viz/dist` is **incorrect** because the `www` directory is not inside `src/server`.

This fragility is why CWD-relative paths are not recommended for server configuration.


**The Solution:** You must use a path that is relative *to the file itself* (`app.ts`) or an absolute path. The modern, Bun-native way to do this is with `import.meta.dir`.


---

## Actionable Resolution Plan
Follow these steps to robustly resolve the path, regardless of where you run the `bun` command.


### 1. Use `import.meta.dir` to Build an Absolute Path
Modify your `src/server/app.ts` to build a reliable path from your file's location.


```
// src/server/app.ts
import { Hono } from 'hono';
import { serveStatic } from 'hono/bun'; // <-- Use the bun-specific import
import { resolve } from 'path'; // <-- Import Node's path module
import { existsSync } from 'fs'; // <-- For debugging

const app = new Hono();

// 1. Get the directory of the *current file*
//    (e.g., /path/to/project/src/server)
const currentFileDir = import.meta.dir;

// 2. Resolve the absolute path to your project's root
//    (This assumes app.ts is two levels deep: /src/server)
const projectRoot = resolve(currentFileDir, '../../');

// 3. Resolve the absolute path to your static assets directory
const staticAssetsPath = resolve(projectRoot, 'www/sigma-viz/dist');

// --- DEBUGGING BLOCK (Add this temporarily) ---
console.log(`[DEBUG] CWD:`, process.cwd());
console.log(`[DEBUG] File Directory:`, currentFileDir);
console.log(`[DEBUG] Project Root:`, projectRoot);
console.log(`[DEBUG] Static Assets Path:`, staticAssetsPath);
console.log(
  `[DEBUG] index.html exists:`,
  existsSync(resolve(staticAssetsPath, 'index.html'))
);
// --- END DEBUGGING BLOCK ---

// 4. Use the absolute path in serveStatic
app.use(
  '/visualization/*',
  serveStatic({
    root: staticAssetsPath,
  })
);

// 5. (Recommended for SPAs) Add a fallback for client-side routing
// This serves index.html for any request under /visualization
// that doesn't match a specific file (e.g., /visualization/some-route)
app.get(
  '/visualization/*',
  serveStatic({
    root: staticAssetsPath,
    path: './index.html',
  })
);

// ... rest of your server code

export default app;

```

### 2. Run and Check Your Logs
When you run your server now, your new debug logs should confirm the paths:



## Answering Your Specific Questions
### 1. Potential root causes for failure outside `src`?
The root cause is **path resolution**. The relative path `./www` is being resolved from the **Current Working Directory (CWD)**, which is likely *not* your project's root directory (or you might be running the command from within `src`, for example).


### 2. Are there Bun limitations or sandboxing?
**No.** Bun does not have a Deno-style file system security sandbox that you need to opt into with flags like `--allow-read`. This is not a permissions or sandboxing issue.


### 3. Best practices for serving static assets (Vite + Hono + Bun)?
You are doing it correctly, with one exception:


- **Use `hono/bun`:** Always use the `serveStatic` middleware from `hono/bun` when running on Bun. It's optimized for the Bun runtime.
- **Use Absolute Paths:** Construct an absolute path for the `root` option using `import.meta.dir` and `path.resolve()`, as shown in the plan above. This makes your server configuration independent of *where* it's run from.
- **SPA Fallback:** Include the `app.get('/*', ...)` fallback route to serve `index.html` for any non-asset requests, which is required for SPAs (like Vite builds) that use client-side routing.

### 4. Specific debugging steps for "File exists: false"?
The debugging steps are exactly those included in the "Actionable Resolution Plan":


1. Log `process.cwd()` to see where the process *thinks* it is.
2. Log `import.meta.dir` to see where your *file* is.
3. Use `path.resolve()` to build an absolute path from `import.meta.dir`.
4. Log this new absolute path.
5. Test the absolute path *directly* with `fs.existsSync(absolutePath)` before passing it to Hono. This isolates the problem completely.

### 5. Could `bun test` or `bun run` change the CWD?
**Yes, absolutely.** This is the core of the problem. `bun run` sets the CWD to the directory you are in when you execute the command. `bun test` may also run from the project root or a different CWD. This variability is precisely why you should *never* rely on CWD-relative paths (`./`) for finding server assets.
