# How AI Coding Agents Think: The Junior Dev with a Superpower

We've all been working more with AI coding agents, and it's clear they are incredibly powerful. They can refactor code, write complex functions, and learn new frameworks in seconds. But they also have a critical, hidden weakness.

Understanding this weakness is the key to working with them effectively.

## The Analogy: A Junior Dev with a Hammer

The best way to think of an AI agent is as a **brilliant, tireless junior developer who just graduated and has zero real-world experience.**

Like a new developer, they are eager to please and incredibly fast. They've read every textbook and memorized every design pattern. But because they lack experience, they often misdiagnose problems.

And when they misdiagnose, they reach for the only "hammer" they know: **refactoring the code or re-architecting the stack.**

## The Crisis: Confusing Activity with Progress

We recently ran into a perfect example of this.

* **The Problem:** A UI component was crashing.
* **The *Real* Cause:** A database query was returning a *massive* amount of data (~200 nodes but ~10,000 edges), which overwhelmed the browser's renderer. It was a **data-volume problem.**
* **The Agent's "Solution":** The agent failed to identify the real cause. Instead, it confidently went on a wild goose chase:
    1.  It first blamed our CDN and re-architected the stack to use NPM packages.
    2.  When that didn't work, it *reversed its own decision*, blaming the NPM packages for causing "context overflows" (a hallucinated, non-existent error).
    3.  It was *doing* a lot, but it wasn't *solving* anything.

The agent lacked the **senior-level experience** to stop and ask the simple question: "Is this even a code problem? Or is the *data* just too big?"

## Your Role: The Senior Developer

This is the most important lesson: **the agent is a tool, not a colleague.**

Your job is to be the "senior developer" or "expedition leader." You must provide the diagnostic strategy. The agent will execute it brilliantly, but it won't *come up with* the right strategy on its own.

To solve this, we now use `OH-126: Data-First Diagnostics`. This is a formal rule we give the agent that *forces* it to check for data-volume problems *before* it's allowed to pick up its hammer and refactor the code.

### Article 2: For the Development Team

```
# The Workbench Protocol (OH-127): A Workflow for AI-Driven R&D

## 1. The Problem: Exploratory Code is Messy

Our "Tree-Climbing" (Accelerated Discovery-Driven Development) strategy is effective but creates two major problems:

1.  **Workflow Friction:** R&D is messy. We create temporary files, test new approaches, and fail often. Being forced to "file" these scraps in the correct `src/` sub-folders *while* we are busy exploring breaks our flow.
2.  **Broken Archives:** Our `BRIEF`/`DEBRIEF` system was failing. We'd start `BRIEF-056`, but by the time we finished, the context was lost, and the archive would be `DEBRIEF-078`. The pairing was disconnected.

## 2. The Solution: The "Workbench vs. Filing Cabinet"

We are adopting `OH-127: Exploratory Programming`. This protocol formally separates our *active work* (the "Workbench") from our *archived work* (the "Filing Cabinet").


## 3. How It Works: The "Workbench" (Active Development)

Your project root is now your "workbench." It's *supposed* to look busy.

1.  **The "Job Ticket":** All new work *must* begin by creating a **`!_CURRENT_TASK.md`** file in the project root.
    * This "shouty" file (the `!` sorts it to the top) is your active `BRIEF`, plan, and scratchpad.
    * It's temporary and will be deleted or archived later.

2.  **The "Work-in-Progress":** To solve all pathing issues, you create your *actual* code files in their **final, permanent location** (e.g., `src/features/my-new-feature/index.ts`).
    * This is not "filing"—this is just putting the work on the bench.
    * All your relative imports (`../../utils`) will be correct from the start.

3.  **The "Pointer":** Your `!_CURRENT_TASK.md` file *must* contain a "POINTER" that points to the code you're working on (e.g., `POINTER: /src/features/my-new-feature/`).

## 4. How It Works: The "Tidy-Up" (The "Filing Cabinet")

When your task is finished (either a success or a failure), you *must* clear your workbench.

### On Failure (You "Climb Back Down")

1.  Delete the `!_CURRENT_TASK.md` file.
2.  Delete the `src/features/my-new-feature` folder.
3.  Your workbench is now clean, and you're ready to start a new task.

### On Success (You "Archive the Findings")

1.  The code in `src/features/my-new-feature` **stays where it is.** It's already in the right place.
2.  Assign a new, consistent ID (e.g., `079`).
3.  **Rename** `!_CURRENT_TASK.md` to `079-BRIEF.md`.
4.  Create your new **`079-DEBRIEF.md`**.
5.  Create a new archive folder (e.g., `archive/079-new-feature/`).
6.  Move *only* the `079-BRIEF.md` and `079-DEBRIEF.md` (and any other *non-code* files) into the archive folder.

---

> **Why We Archive:** The reason we formally archive our `BRIEF` and `DEBRIEF` files is to build a knowledge base. This allows us to harvest valuable **lessons-learned** from every task—successful or not—to improve our future processes.

```

1. **The Registry:** This is a massive online database (the world's largest software registry) where all these public packages are stored.

- `npm install <package-name>`: Add a new package to their project.

- `npm uninstall <package-name>`: Remove a package.
