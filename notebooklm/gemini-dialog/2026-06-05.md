How AI Text Detection Works
Detecting whether a text was written by a human or AI is not easy. One famous example includes AI detection software flagging the Declaration of Independence from the year 1776 with a probability of 98.51% as AI-generated [3].
LLMs evolve, so the writing style changes with each new LLM release. Additionally, people can avoid AI writing detection by using specific prompts to avoid certain telltale signs or by rephrasing sentences to confuse detection models.
The 4 Main Types of AI Text Detection Systems
Detecting AI-generated text remains an active area of research. As shown in the figure below, detection methods can be classified into four categories.

Watermarking Technology: The LLM provider embeds invisible digital watermarks in generated text. For instance, Google embeds SynthID watermarks in its AI-generated images, audio files, texts, and videos. These watermarks can be used to detect AI-generated content.
Statistics-Based Detectors: These detectors analyze different text features to detect statistical patterns in AI-generated text. Perplexity and Burstiness: Popular Signals Used by AI Detectors
Besides the research, many AI detection tools focus on statistics-based detection, including perplexity and burstiness [5].
Perplexity is a white-box statistic that uses an LLM to measure the likelihood of the next word. For instance, given the text “I would love a bowl of ___,” an AI would most likely predict the word “soup.”
A human writer, however, might write something more unpredictable, such as “I would love a bowl of the soup you made for my birthday last year.” AI-generated text tends to have low perplexity, while human-generated text tends to have high perplexity.
Burstiness measures the variation in sentence length and structure. AI-generated text tends to be less bursty, usually meaning medium sentence length and consistent structure. Human-generated text, on the other hand, has more variation.

How ZeroGPT Flags AI-Written Text

These signals include token patterns, burstiness, entropy, and ensemble classifier features trained on mixed datasets. The output is an overall score and highlighted passages that appear to be AI-generated [6].
How GPTZero Detects AI-Generated Writing
GPTZero is one of the most widely used AI detection models. The latest version falls into the “Neural-Based Detectors” category. It uses a deep learning AI model that is trained on human-written text data and AI-generated text from various popular LLMs. The model classifies each sentence and provides a probability that it was generated by AI, by humans, or both [7, 8].

from typing import Type, TypeVar

from google import genai
from google.genai import types
from pydantic import BaseModel

client = genai.Client()

T = TypeVar("T", bound=BaseModel)


def call_llm(prompt: str, response_model: Type[T]) -> T:
    """Make a structured LLM call conforming to the provided Pydantic model"""

    config = types.GenerateContentConfig(
        temperature=0.0,
        thinking_config=types.ThinkingConfig(thinking_level="minimal"),
        response_mime_type="application/json",
        response_json_schema=response_model.model_json_schema(),
    )

    response = client.models.generate_content(
        model="gemini-3.1-flash-lite-preview",
        contents=prompt,
        config=config,
    )

    text = response.text

    try:
        return response_model.model_validate_json(text)
    except Exception as e:
        raise ValueError(f"Invalid structured output:\n{text}") from e

        description="Estimated probability that the text was written by AI, from 0 to 100",
    )
The AllCategoryResults class aggregates each category score in a structured way. This will be used as input to generate a final verdict. The Verdict class is the LLM’s output, providing a probability between 0 and 100 of how likely the text is to be AI-generated.
The score_category() function reads a single category from the YAML file and instructs the LLM on how to evaluate the text provided. The goal is to score each category independently.
def score_category(category: dict, text: str) -> CategoryScore:
    examples_str = "\n".join(category["examples"])
    prompt = f"""
You are an expert linguistic evaluator. Your task is to assess whether the given text exhibits a specific writing pattern.
You must be precise, consistent, and conservative in your judgments. Do not overgeneralize or infer intent beyond the text.

## EVALUATION CATEGORY:
Name: {category["name"]}

Definition: 
{category["description"]}

Examples (for calibration only, do NOT copy wording or assume exact matches are required):
{examples_str}

## SCORING GUIDELINES
Score from 1 to 5 based on how strongly the pattern is present:

1 = Not present at all
2 = Possibly present (weak or ambiguous signal)  
3 = Moderately present (clear instance, but limited or isolated)  
4 = Strongly present (multiple clear instances or a dominant pattern)  
5 = Very strongly present (pervasive, defining characteristic of the text)

Important:
- Base your score ONLY on observable text features.
- Do NOT rely on assumptions about the author or intent.
- Do NOT penalize or reward general writing quality.
- The pattern must match the definition, not just vaguely resemble it.

## OUTPUT FORMAT:
Return JSON with:
- reasoning: brief explanation of your decision
- score: 1-5

## INPUT TEXT:
{text}
""".strip()

    return call_llm(prompt, CategoryScore)
The final_verdict() function uses the aggregated scores from all the categories to generate a final verdict. I also added a short prompt about the word count because text that is too short is unreliable, so stronger evidence is needed in that case.
def final_verdict(categories: AllCategoryResults, word_count: int) -> Verdict:
    prompt = f"""
You are an impartial judge. Your task is to estimate the probability that a text was written by an AI system.
You MUST base your decision strictly on the provided category scores and reasoning.

## INPUT CATEGORY SCORES:
Each category includes:
- a score from 1 (not present at all) to 5 (very strongly present)
- reasoning describing the evidence

{categories.model_dump_json(indent=2)}

## OUTPUT PROBABILITY GUIDELINES
Use these rough anchors for calibration:

- 0-20: little to no evidence of AI patterns
- 21-40: weak or sparse signals
- 41-60: mixed or moderate evidence
- 61-80: strong evidence across multiple categories
- 81-100: overwhelming and consistent AI-like patterns

When in doubt, favor the human-written hypothesis: unless the evidence is both strong and consistent, keep the probability close to 50 rather than assigning a high AI likelihood.

## LENGTH ADJUSTMENT RULES
Text length: {word_count} words
- <50 words: low reliability -> reduce confidence
- >=200 words: higher reliability -> increase confidence

## OUTPUT FORMAT:
Return JSON with:
- reasoning: brief explanation of your decision
- ai_probability: estimated probability from 0 to 100
""".strip()

    print(prompt)
    return call_llm(prompt, Verdict)
The analyze_text() function runs the whole pipeline. It returns a dictionary that contains each category and also the final verdict.
def analyze_text(text: str) -> dict:
    """Run each category rubric, then feed results into final verdict prompt"""

    results = {}
    for c in CATEGORIES:
        results[c["name"]] = score_category(c, text)

    category_results = AllCategoryResults(results=results)

    word_count = len(text.split())
    verdict = final_verdict(category_results, word_count)

    return {"rubrics": category_results.model_dump(), "verdict": verdict.model_dump()}

Conclusion
In this project, we implemented the LLM-as-a-judge concept to automatically evaluate a text using a community-generated list of signs of AI-generated writing from Wikipedia.
I tested the concept on two human-written texts and three AI-generated texts, achieving fairly good results.
Of course, there are a few improvements that could be made. First, I did not implement every rule from Wikipedia’s list. For example, “overuse of boldface” is a strong indicator, but this does not work when copying and pasting simple text into a text field.
Perhaps there are other great lists of AI indicators that are not targeted solely at Wikipedia articles. Other categories could easily be added to the YAML configuration file. Here on Medium, for example, I consider AI-generated top images and infographics to be a strong indicator of AI usage.
Unfortunately, Wikipedia’s list of AI signs can be used to game the system by prompting an LLM to avoid all these signs. This is why relying purely on that list is not enough to detect skillful AI usage.
A great solution for detecting AI writing would be to combine multiple categories from the research summary on how AI text detection works. The Wikipedia list is a human-assisted method. A valuable improvement would be to add a statistics-based method. For example, one could evaluate perplexity and burstiness as additional signals to make the overall pipeline more robust and accurate.

### 2. Potential Benefits
Beyond the immediate utility of an AI text detector, this exercise offers several architectural benefits for your ongoing projects:


- **Schema-as-Contract:** It forces you to define clear, typed contracts for LLM outputs. This is a foundational practice for your "Persona Engineering" stack.
- **Composable Reasoning:** By breaking the "judge" into discrete categories (YAML-based rubrics), you are essentially building a **Pipeline Registry**. You could easily repurpose this pattern for other classification tasks (e.g., policy compliance, tone analysis, or sentiment extraction).
- **Data Integrity:** You gain experience in handling "LLM drift"—where models change over time—by decoupling your evaluation rubrics (YAML) from the execution logic (TypeScript code).

### 3. Is the project overcomplicated?
**Opinion:** The project is **appropriately scoped**, not overcomplicated.


The author’s decision to use a YAML-defined rubric is actually a *simplification* strategy. By externalizing the "signs of AI" into data rather than hard-coding them into prompts or model weights, they have created a system that is:


1. **Auditable:** You can inspect the rubric independently of the code.
2. **Maintainable:** Adding a new "sign" of AI is a configuration change, not a code change.
3. **Deterministic-ish:** By using `temperature=0.0` and structured output, you are maximizing the consistency of a non-deterministic process.

**Recommendation:** If you decide to proceed, treat this as a "Silo" module. Keep the rubric parsing and LLM orchestration entirely isolated. This will allow you to drop this detection module into your future "Master Context" or other agentic frameworks with zero friction.
